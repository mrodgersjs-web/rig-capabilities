## ADDED Requirements

### Requirement: Reject unsupported offering identity
The site gate SHALL require a named client or a directly user-named private project, client branding and a source-located solution chain.

#### Scenario: TransformFit private project
- **GIVEN** independently verified direct user identity evidence for TransformFit and complete source references
- **WHEN** offering identity is validated
- **THEN** a public domain SHALL NOT be required or invented

#### Scenario: Category desk and RIG brand
- **GIVEN** only a generic category buyer or a RIG-branded offering
- **WHEN** the client-offering count is evaluated
- **THEN** that offering SHALL NOT count

### Requirement: Bind acceptance to authorized independent evidence
The gate SHALL validate every consumed artifact, immutable build, served URL, capture session and authenticated independent verifier against an existing approved trust root.

#### Scenario: Caller-generated signer
- **GIVEN** a caller-selected public key without approved website-QA authority
- **WHEN** the gate is run
- **THEN** it SHALL return FAIL without enrolling the key

#### Scenario: Artifact mutation
- **GIVEN** previously accepted fixture artifacts
- **WHEN** a bound artifact or build changes
- **THEN** a rerun SHALL reject the stale receipt

### Requirement: Observe real interaction and QA
Acceptance SHALL require desktop/mobile scroll and reactive 3D observations, a usable reduced-motion alternative, actual CTA interaction, original mobile Lighthouse JSON, decoded captures and resolved independent critique findings.

#### Scenario: CSS 3D
- **GIVEN** genuine observed CSS 3D depth/rotation responding to actual inputs
- **WHEN** 3D evidence is validated
- **THEN** a WebGL canvas SHALL NOT be required

#### Scenario: Copied scores and source tokens
- **GIVEN** source animation comments, a static perspective declaration or copied high Lighthouse values
- **WHEN** acceptance runs
- **THEN** those assertions SHALL NOT satisfy runtime evidence requirements

### Requirement: Execute all Miro phases per offering
The gate SHALL require ordered native Miro progression with real phase artifacts and three rendered divergence directions.

#### Scenario: Process setup alone
- **GIVEN** seven Markdown files or new process frames without per-offering execution artifacts
- **WHEN** phase progression is validated
- **THEN** it SHALL fail

### Requirement: Count offerings without inflating clients
Portfolio acceptance SHALL rerun all site gates and count at least ten distinct client-branded offerings, allowing several supported offerings for one client.

#### Scenario: Duplicate mechanism
- **GIVEN** renamed copies or duplicate solution mechanisms
- **WHEN** the portfolio is counted
- **THEN** they SHALL NOT increase the accepted count
